# v0.3 — Memory Agent

## Goal

Turn Lunar Arcana from a single-session AI tarot reader into a lightweight tarot agent that can remember previous readings, compare them across time, and learn from the user's later reflections.

The core product idea for v0.3 is:

> A tarot reader that remembers your journey.

This release should preserve the current local-first, lightweight TUI architecture. Do not introduce a heavy agent framework, vector database, hosted backend, or mandatory account system.

## Product loop

```text
question
  ↓
reading
  ↓
interpretation
  ↓
persist episode
  ↓
reflection / outcome
  ↓
retrieve relevant history
  ↓
future interpretation
```

The purpose of memory is not to claim better prediction. Memory should make the interpretation more context-aware, longitudinal, and useful for reflection.

## Scope

### 1. Reading history — episodic memory

Persist completed readings locally.

Initial storage target:

```text
~/.lunar-arcana/readings.jsonl
```

Suggested record shape:

```python
@dataclass(slots=True)
class ReadingRecord:
    id: str
    created_at: datetime
    question: str
    cards: tuple[DrawnCard, DrawnCard, DrawnCard]
    interpretation: str
    follow_ups: list[ConversationTurn]
    reflection: str | None = None
    outcome: str | None = None
```

Requirements:

- Save only after a concrete reading exists.
- Preserve the exact cards and orientations that were drawn.
- Store the generated interpretation separately from the immutable reading data.
- Keep storage local and human-inspectable.
- Failure to write memory must not corrupt or block the reading flow.

### 2. History view

Add a TUI history surface for browsing previous readings.

Minimum information:

- date/time
- original question
- three cards
- whether reflection/outcome exists

A user should be able to open an old reading and inspect its original interpretation and follow-up conversation.

### 3. Reflection / outcome

Allow the user to revisit an old reading and record what happened later.

Suggested lightweight states:

- broadly aligned with the earlier interpretation
- partly aligned
- substantially different
- still unresolved

The user can also add free-form notes.

Outcome data is reflective feedback, not evidence that tarot predicts the future. The UI and prompts should preserve that distinction.

### 4. Relevant-memory retrieval

Before a new AI interpretation, retrieve a small number of relevant previous readings.

v0.3 should start with simple deterministic retrieval rather than embeddings.

Candidate signals:

- keyword overlap in questions
- recurring domain terms such as work / study / relationships / decisions
- repeated cards
- recency

Return only a small bounded context set, for example the top 1–3 readings.

The interpreter should receive:

```text
current question
+ current cards
+ compact summaries of relevant previous readings
+ reflections/outcomes when available
```

Do not blindly replay the entire history into the model.

### 5. Cross-reading interpretation

The model may reference relevant previous readings when useful.

Example behavior:

> A similar theme appeared in your earlier reading about changing projects, but the current situation differs in one important way...

Constraints:

- Never claim that repeated cards prove fate, destiny, or a fixed future.
- Distinguish remembered user-provided facts from tarot-derived interpretation.
- If an old interpretation was contradicted by later reality, acknowledge the mismatch instead of rationalizing it away.
- Historical context should support reflection, not increase certainty.

## Architecture

Keep the current domain/interpreter separation and add a small memory layer.

Suggested structure:

```text
tarot_tui/
├── app.py
├── cards.py
├── domain.py
├── interpretation.py
├── memory.py        # records, storage, retrieval
└── ...
```

Possible interfaces:

```python
class ReadingStore(Protocol):
    def append(self, record: ReadingRecord) -> None: ...
    def list(self) -> list[ReadingRecord]: ...
    def get(self, record_id: str) -> ReadingRecord | None: ...
    def update_reflection(self, record_id: str, reflection: Reflection) -> None: ...


class MemoryRetriever(Protocol):
    def retrieve(self, question: str, *, limit: int = 3) -> list[ReadingRecord]: ...
```

Keep persistence and retrieval independent from the OpenAI interpreter so they remain testable without network access.

## Non-goals for v0.3

Do not expand scope with:

- vector databases
- LangChain / agent frameworks
- cloud sync or user accounts
- astrology or numerology
- many new spreads
- automatic claims about personality
- autonomous proactive messaging
- prediction scoring

These can be reconsidered after the memory loop is proven useful.

## Implementation sequence

### Milestone 1 — Persist episodes

- Define serializable memory-domain types.
- Implement JSONL local store.
- Save completed readings.
- Add unit tests for round-trip serialization, malformed rows, and write failures.

### Milestone 2 — Browse and reflect

- Add history view.
- Open previous reading details.
- Add reflection/outcome editing.
- Test empty history, many records, and legacy/no-memory startup.

### Milestone 3 — Retrieve relevant history

- Implement deterministic ranking.
- Bound retrieved context to 1–3 readings.
- Add retrieval tests with controlled examples.

### Milestone 4 — Memory-aware AI reading

- Extend interpreter input with retrieved memory summaries.
- Add prompt rules for separating fact, memory, and symbolic interpretation.
- Add tests ensuring unrelated history is omitted and current fixed cards remain authoritative.

### Milestone 5 — Cross-reading UX polish

- Clearly mark when an interpretation references history.
- Allow users to inspect which prior readings were used.
- Add an option to disable memory for a reading.

## Acceptance criteria

v0.3 is complete when all of the following are true:

1. A completed reading survives application restart.
2. The user can inspect previous readings from the TUI.
3. The user can attach a later reflection/outcome to an old reading.
4. A new reading can retrieve a bounded set of relevant historical readings without a vector database.
5. The LLM can use that history while clearly distinguishing remembered facts from symbolic interpretation.
6. Memory can be disabled without breaking the existing reading flow.
7. Existing no-API-key local interpretation continues to work.
8. Tests cover persistence, retrieval, and memory-aware context construction.

## Later direction

After v0.3 validates the memory loop, possible follow-ups include:

- semantic user themes derived from repeated episodes
- recurring-card and recurring-topic journal views
- explicit memory management (view / edit / forget)
- optional local embeddings for larger histories
- longitudinal summaries such as monthly or yearly reflection

The important progression is:

```text
single reading
→ persistent episodes
→ reflection
→ retrieval
→ longitudinal interpretation
```

v0.3 should stop there and prove that this loop is useful before adding broader features.
